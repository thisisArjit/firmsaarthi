# Placement, loading and arrival evidence

27 October 2026. Unpublished next increment after release 40. Policy/snapshot/file/review APIs, enforced physical/follow-up transactions and opt-in event routing are prepared locally. Candidate migrations 0028–0034 have not been applied to hosted databases; the complete milestone UI and hosted validation remain pending. The local API now uses actual prerequisites instead of the temporary 503. Production remains release 40. Do not describe this document as a delivered workflow.

## First usable scope

Keep the simple Initiated → In progress → Complete consignment summary. Within trip progress, add explicit placement, loading and arrival records, with actual time, recorded time and actor. These are manual operational claims. GPS observations, operational completion, uploaded files and owner acceptance remain separate facts. None changes invoice recognition or payment state.

The evidence checklist has three explicit rules, each optional or accepted-file-required:

| Stage | Evidence scope | Missing-file explanation |
| --- | --- | --- |
| Placement | One private file on the trip, with no allocation ID | Placement confirmation needs an accepted file |
| Loading | A separate accepted private file for each active consignment allocation | Name the consignment still missing loading confirmation |
| Arrival | A separate accepted private file for each active consignment allocation | Name the consignment still missing arrival confirmation |

Optional means the file checklist is empty, not that the physical event happened. This deliberately excludes POD, which retains its existing independent required-file contract. Operational attachments cannot be counted as private stage evidence, and a private stage file cannot count as POD. A copied byte stream still needs its own scoped record and review.

Use confirmation photos or business documents only. Do not request Aadhaar, PAN, driving-licence copies, bank records or identity verification through this feature. Driver/owner contact details and future consent-based KYC are separate workstreams. Upload authenticity and owner review remain manual; do not claim government/provider verification.

## Domain contract prepared locally

`lib/trip-stage-evidence.ts` parses an explicit version-1 policy with exactly placement/loading/arrival rules. It rejects omissions, unknown keys, unsupported versions and coercions; it returns a copied frozen snapshot. There is no absent-policy fallback: the later integration must explicitly preserve legacy behavior for trips without this contract.

The checklist accepts a **trusted server projection**, after tenant-scoped database joins and authorization. It returns missing file slots only. It does not authenticate anyone, authorize an API, validate event chronology, freeze a database row or allow a transition. A caller must never construct that projection from submitted document metadata or client-selected tenant/role fields.

Only a matching tenant/trip/stage/private-purpose record with an uncorrected acceptance made by an OWNER qualifies. Pending uploads, rejection, corrected acceptance, operational/POD purposes, inactive/wrong allocations, member/dispatcher reviews and foreign records do not satisfy requirements. Empty active-allocation sets and ambiguous duplicate document IDs fail closed. One file cannot be projected as evidence for multiple consignments. The review role is recorded at review time; changing a person's later role does not silently rewrite historical acceptance.

Unique object keys isolate concurrent attempts. A failed transaction removes only that attempt's bytes.
