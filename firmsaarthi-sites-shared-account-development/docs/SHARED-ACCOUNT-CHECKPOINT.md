## Implemented local workflow

Transport Settings → Company website opens Sites in a new tab. With FIRMSAARTHI_SSO_ENABLED=true on both validated deployments, it starts /api/auth/firmsaarthi/start. Otherwise the entry remains the ordinary Sites homepage link and the new flow rejects access. The existing Transport session (Google or password) authenticates the handoff; if expired, a host-only continuation cookie returns from the normal Transport login. Passwords/cookies are never forwarded to Sites or shared through a parent-domain cookie.

Sites creates browser-bound random state, then its existing signed/replay-protected server bridge requests a one-use ticket from Transport. The Transport browser endpoint validates its enabled account/membership/session and returns a hashed,60-second one-use code to a fixed Sites callback. Signed server exchange returns the immutable Transport user ID, normalized email, current credential version and source-session hash, with an exact issuer. No Transport role, administrator permission, financial/customer record or plan is transferred. Referrer-policy/no-store/host-only HttpOnly Secure cookies protect the handoff; URL parameters carry only short-lived opaque capability/state, never email, passwords or raw sessions. New rows reuse the existing bridge table with separate account-* phases, so Transport adds no migration.

First linking always requires the normal Sites email OTP and explicit checkbox consent to link the account and sign out earlier Sites sessions. This is intentional even when the current Transport legacy password account has the same Gmail: the address alone is not mailbox ownership. The unique mapping is Transport immutable user ID → existing Sites user ID. Existing website ownership, optional legacy Sites password, Google binding and plan records are preserved. A different signed-in Sites account or a second Transport identity cannot take a linked Sites owner. Two mapping uniqueness constraints and transactional review consumption prevent competing links. No new password is created/reset by this workflow.

Returning shared sign-in reuses that mapping without another email code. Sites sessions bind the central credential version; SSO-created sessions also bind the originating Transport session hash. Signed back-channel checks fail closed on central disable, membership loss, credential replacement, source-session expiry/logout or unavailable bridge. A fresh shared sign-in after credential replacement does not revive earlier Sites sessions. Independent legacy Sites sign-in is retained; global logout of every product/provider session is not implemented. No Google-provider logout, credential/password migration, cross-product role grant, Transport-plan inheritance or automatic business-data import is claimed.

New Sites migration0005_shared_firmsaarthi_account is generated schema-only: browser flows, pending reviews, unique immutable identity links and federated-session metadata. Prior Sites migrations/snapshots/journal entries remain unchanged. Both feature flags are absent/disabled in real hosting. Staging URL selection explicitly rejects production Transport integration URLs when APP_ENV=staging; only the existing private Transport stage origin is permitted. No staging application may point mutation/mail/payment/identity QA at production.
