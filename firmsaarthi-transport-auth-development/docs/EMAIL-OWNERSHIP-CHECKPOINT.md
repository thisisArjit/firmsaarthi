## Implemented locally

Isolated checkout: ../tms-auth-release, opened from the existing production Site source through the supported Sites source helper. No new Site or account was registered. This candidate is NOT the authoritative published Transport checkout, which remains ../tms-payments-release.

- Additive migration0037 creates short-lived signup challenges and separate account-email evidence. It performs no update/backfill of existing accounts, credentials, sessions or memberships. Drizzle's schema model includes both tables.
- SignupEmailProof requests a six-digit mailbox code, validates it in the requesting browser, then permits a fresh password/business name. Pending challenges never create/reserve an account or store a chosen password. The registered address comes from the verified server-side challenge, never a completion-body email/role/org.
- Random256-bit request/browser/registration capabilities are stored as hashes; codes and payload-recovery digests are purpose-separated HMACs. Ten-minute code expiry, five attempts, shorter five-minute completion, cooldown and per-IP/address limits apply. A resend from a different browser does not invalidate an owner's existing proof.
- Existing/disabled addresses and failed delivery return the same generic message and cannot authorize registration. SMTP delivery is injected; tests use only synthetic in-memory senders. No provider credential, real email or customer document was used.
- Signup and password reset intentionally share the existing reset daily-budget key when using the SAME protected email secret and budget (production70, staging20). Integration must preserve this shared config; no second independent free-mail allowance is added. Invalid/unbounded candidate budgets fail closed. Counted attempts are not proof of delivery or free provider capacity.
- Completion atomically consumes the proof and creates one own workspace, password account, OWNER membership, evidence and audit. Exact retries recover the same receipt; changed payloads or conflicting existing password/Google accounts cannot merge or overwrite anything. Disabled/changed-credential/changed-role recovery is denied. Audit failures roll the entire transaction back.
- This new-registration-only service requires at least15 Unicode code points, with the existing128-code-unit maximum for hashing compatibility. Existing eight-character passwords and every existing authentication route remain unchanged. A breached-password blocklist and MFA are not implemented by this service.

## Dated primary-source review

Reviewed29October2026: [OWASP email verification](https://cheatsheetseries.owasp.org/cheatsheets/Email_Validation_and_Verification_Cheat_Sheet.html) calls for expiring, single-use ownership proof before account activation; email is a weak factor, so it does not replace MFA. [OWASP federated linking](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html#secure-federated-account-linking) recommends re-authenticated linking rather than matching profile attributes alone. [Google OIDC](https://developers.google.com/identity/openid-connect/openid-connect) defines stable subject identity and warns against using a mutable email as the primary identity key. Product decision: prove a new mailbox before creating its password account, keep existing identity/history intact, and finish explicit legacy account-claim protection before declaring the broader gap closed. No competitor/provider asset or claim was copied.
